CCMMD — system architecture

Event-driven chess platform: nine Spring Boot services behind one gateway, with a React SPA.

9 services 12 containers 5 databases 134 backend tests 13 frontend tests AI: Stockfish 19 (UCI) broker: RabbitMQ
a request travels the solid path session pinned in Redis state and events leave the service

1 · Sign in

  1. Browser posts credentials to nginx → api-gateway.
  2. Gateway calls auth-service, which verifies BCrypt and returns {user, token, expiresAt}.
  3. Gateway keeps the token in the session (Redis) and sets an httpOnly cookie. The browser never sees a JWT.
  4. On each proxied call the gateway swaps the session for a short-lived Bearer JWT; services verify it against auth's JWKS.

2 · Make a move

  1. The move is synchronous: gateway → game-service → chesslib.
  2. Applied in one transaction with optimistic locking, then announced via the outbox.
  3. game.move.played reaches presence; game.ended reaches notification and analysis.
  4. Chess is never eventually consistent — only the announcements are.

3 · Play the computer

  1. Human moves; game-service writes engine.move.requested in the same transaction.
  2. engine-service drives Stockfish over UCI and replies engine.move.computed.
  3. Correlation id is gameId:ply, so a late or duplicated answer is ignored.
  4. The reply is applied through the same validation path as any human move.

4 · Find an opponent

  1. Two players queue in matchmaking-service (its own database, not Redis).
  2. A scheduled matcher pairs them under row locks, so two replicas cannot pair one player twice.
  3. matchmaking.match.found carries a pre-allocated gameId.
  4. game-service creates the game under that id — idempotent on the id, not on the event.

Why the move path is synchronous: a move is validated and applied by one writer, then announced. Routing it through the broker would make the board eventually consistent, which chess cannot tolerate. Everything that can lag — presence, notifications, analysis, the public game list — goes over the bus.

Why each service owns its outbox: state and announcement must commit together. A service with no durable state (engine, presence) publishes directly instead, because there is no dual write to protect.
